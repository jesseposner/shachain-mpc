# WAN measurements: the current system

Date: 2026-08-24. Four `c7g.2xlarge` (Graviton, 8 vCPU), Ubuntu 24.04 arm64,
one per region, joined by a WireGuard mesh. Iceberg t=2: a quorum of three
online members tolerating one corruption, plus a standby. Malicious security
throughout. Raw logs in `wan2/`.

This run measures the system as it now stands. The earlier run
(`wan-20260823.md`) measured a version whose payment path, recovery and key
material have all since changed, and which was still computing the wrong
answer in every lane but the first of a batched hash.

## Latency

| from \ to | m0 us-east-1 | m1 us-west-2 | m2 eu-west-1 | m3 eu-central-1 |
|---|---|---|---|---|
| m0 us-east-1 | - | 57.3 ms | 68.6 ms | 91.4 ms |
| m1 us-west-2 | 57.3 ms | - | 118.6 ms | 139.7 ms |
| m2 eu-west-1 | 68.6 ms | 118.6 ms | - | 19.7 ms |
| m3 eu-central-1 | 91.4 ms | 139.1 ms | 19.7 ms | - |

Every leg is within about two milliseconds of the previous run, so the two
are comparable and any difference is the system rather than the network.

## A revocation is one round

| | before the quorum change | after |
|---|---:|---:|
| the quorum's slowest leg | 118.6 ms | 139.7 ms |
| **measured release** | **139 ms** | **184 ms** |

Twice at 139 ms, twice at 184 ms. The release cost tracks the slowest leg of
whichever quorum is online, which is what a single round should do and what
nothing was fitted to predict.

Revealing a prepared secret runs no MPC. Each member derives the summands it
holds and sends them, the adapter compares the copies, XORs them into the
public masked value, and checks the result against the point published
earlier. Compute is about 60 microseconds, almost all of it the one elliptic
curve multiplication in that check, against 139 ms of network.

What is measured here is one revocation, which is what one commitment update
consumes. A payment is normally two updates, one carrying `update_add_htlc`
and one carrying `update_fulfill_htlc`, so an isolated payment pays this
twice at different moments; a channel batching HTLCs into shared commitments
pays it less often than once per payment.

## A quorum change costs nothing

Member 2 in Ireland dropped mid-channel and the standby in Frankfurt took
over. Nothing was rebuilt, and the channel continued:

```
== crash: volatile state destroyed; member 2 offline
== quorum change to [0, 1, 3], continuing without a rebuild
== continuing: 2 updates with the new quorum
== distributed PoC complete: LDK accepted every point and secret
```

The previous run measured what this replaced: a 77,151-round rebuild from
the seed, 126 minutes, with the channel frozen throughout.

## Per-primitive costs

| step | rounds | this run | previous run |
|---|---:|---:|---:|
| SHA-256 edge | 1,614 | 65.5 s | 65.0 s |
| scalar validity check | 16 | **0.61 s** | 10.2 s |
| Boolean to Z_q conversion | 31 | 1.64 s | 1.63 s |
| edge, check and conversion | 1,665 | **67.9 s** | 77.0 s |
| 100 edges batched | 1,880 | **77.9 s** | 86.1 s |

The validity check fell from 10.2 s to 0.61 s because the comparator became
a balanced tree rather than a 256-step carry chain. That change was found by
this deployment's round counts, made on one machine where it looked like a
curiosity, and is confirmed here at the scale that motivated it.
The batched row is worth more than its number: the previous run's equivalent
was measured on a code path that computed the wrong answer in every lane but
the first. This is 100 verified-correct parallel hashes, costing 17% more
wall-clock than a single edge.

## The lifecycle

```
dealt 4 Iceberg shares of 3 seeds each
cold start, 48 edges, 77,151 rounds        3160.0 s
state 0, no new edge                          6.9 s
state 1, no new edge                          7.2 s
state 2, one new edge                        82.1 s
crash, quorum change, no rebuild
state 3, no new edge                          8.5 s
state 4, two new edges                      172.1 s
total                                      3437.7 s
```

Per-update costs follow the shachain schedule exactly: commitment c needs
v2(c) new edges, so most updates need none and cost only the export path,
while c=2 needs one edge and c=4 needs two. The 6.9 to 8.5 s figures are
about 2.3 s of MPC and the rest per-step compilation, which a production
engine does once rather than every step.

## What is not here

`release_only`, which measures the older six-round MPC form of a release,
failed in this run: the benchmark phase writes an input file only for party
0, while that program takes an input from all three. The manual invocation
that worked against the previous cluster copied the file by hand and the
script never learned to. It costs about five minutes to re-run once fixed,
and only affects the comparison against the older form; the one-round
measurement above does not depend on it.
