# WAN measurements: three continents, 2-of-4

Date: 2026-08-23. Four `c7g.2xlarge` (Graviton, 8 vCPU), Ubuntu 24.04 arm64,
one per region, joined by a WireGuard mesh. This is Iceberg's t=2: quorum of
2t-1 = 3 online members tolerating one corruption, plus a standby. Malicious
security throughout. Raw logs in `wan-live/`.

| member | region | role |
|---|---|---|
| 0 | us-east-1 | quorum slot 0; coordinator and LDK counterparty |
| 1 | us-west-2 | quorum slot 1 |
| 2 | eu-west-1 | quorum slot 2 |
| 3 | eu-central-1 | standby, takes slot 2 after the quorum change |

## Latency

Measured over the mesh, which is the path the MPC takes.

| from \ to | m0 us-east-1 | m1 us-west-2 | m2 eu-west-1 | m3 eu-central-1 |
|---|---|---|---|---|
| m0 us-east-1 | - | 54.7 ms | 67.7 ms | 91.2 ms |
| m1 us-west-2 | 54.7 ms | - | 117.8 ms | 142.8 ms |
| m2 eu-west-1 | 67.7 ms | 117.7 ms | - | 19.4 ms |
| m3 eu-central-1 | 91.2 ms | 142.7 ms | 19.4 ms | - |

The active quorum's slowest leg is 117.8 ms (us-west-2 to eu-west-1).

## Per-primitive costs

| step | rounds | loopback | WAN | ms per round |
|---|---:|---:|---:|---:|
| one shachain edge (SHA-256) | 1,614 | 55 ms | **65.0 s** | 40.3 |
| scalar validity check | 256 | 8 ms | 10.2 s | 40.0 |
| Boolean to Z_q conversion | 31 | 5 ms | **1.63 s** | 52.4 |
| 100 edges batched | 2,106 | - | 75.3 s (**0.75 s per edge**) | 35.8 |

The batched row was measured before a correctness fix: vectorised hashing
was wrong in every lane but the first, because `circuit.sha256` builds its
constants one bit wide. The corrected circuit is nearly the same size (64
lanes cost 1,775 rounds against 1,621 for one), so the cost stands, but that
run did not demonstrate 100 correct hashes. See docs/batching.md.

Party-0 traffic is unchanged from loopback: 0.48 MB for one edge, 4.35 MB for
a hundred. Bandwidth was never the constraint and still is not.

## What the numbers settle

**Rounds times latency governs, and now it is measured rather than argued.**
Wall-clock per counted round is 40.3, 40.0 and 35.8 ms across three
independent measurements of very different circuits. That is close to the
mean one-way hop of the three-party ring ((27.4 + 58.9 + 33.9) / 3 = 40.1 ms),
which is what a protocol where each party sends to one neighbour should cost,
rather than a round trip on the slowest leg. One SHA-256 edge over three
continents is 65 seconds against 55 milliseconds on one machine: a factor of
about 1,180, entirely attributable to the ~1,600 sequential rounds inside the
circuit.

**Derivation cannot sit on the payment path, so the lookahead buffer is a
requirement rather than an optimization.** A 65-second per-commitment
derivation leaves nothing to argue about.

**Batching survives the WAN intact.** A hundred independent chains cost 16%
more wall-clock than one (2,106 rounds against 1,875), amortizing to 0.75 s
per edge. The multi-channel throughput story carries over from loopback.

**The hot path is 1.63 s, not the "well under a second" predicted.** The
conversion is 31 rounds and behaves exactly as the round model says; the
earlier estimate was simply optimistic by about a factor of two. It remains
comfortably inside a payment's tolerance, but the honest figure is 1.6 s per
update, plus a scalar opening.

**A cheap optimization only the WAN revealed.** The validity check costs
10.2 s because `less_than_const` is written as a 256-step serial carry chain,
invisible at 8 ms on loopback. Tree-reducing it to ~8 rounds of depth would
cut it to roughly 0.3 s, taking about a third off the per-update hot path.
This is now the most attractive remaining micro-optimization.

**Cold start over a WAN is tens of minutes whichever protocol runs it**: 48
sequential edges is 48 x 65 s, near 52 minutes, and MP-SPDZ garbles the same
circuit over many rounds as well. That cost is exactly why
the garbled package has to be stockpiled before the channel exists, and why
evaluating a stockpiled package in two rounds is the result that matters for
channel open.

## The lifecycle: channel open from a stockpiled package

Full distributed run, 2-of-4, coordinator on member 0, live LDK
counterparty judging every point and secret (`wan-live/lifecycle.txt`):

```
== setup: dealing RSS summands member-to-member
== pre-garbled channel-open package stockpiled (4538.0s, before the seed is used)
== channel open: 48-edge cold start via stockpiled garbled package
   cold start 4.8s
== steady state: 3 updates
   state 0: point published (16.7s)
   state 1: point published, state 0 revoked (20.3s)
   state 2: point published, state 1 revoked (94.6s)
== distributed PoC complete: LDK accepted every point and secret
```

**Channel open across three continents took 4.8 seconds.** The same 48-edge
cold start computed on the critical path would be 48 sequential edges at
65 s each, near 52 minutes. None of the work disappeared, since garbling
itself took 76 minutes. It moved to before the channel, and before the seed,
existed, which is the entire claim the WAN run was built to test.

The per-update figures decompose exactly as the schedule predicts. A leaf at
commitment number c costs v2(c) new hash edges, so states 0 and 1 need none
and cost only the export path (validity check 10.2 s plus conversion 1.6 s
plus overhead), while state 2 needs one edge and pays 65 s more. The measured
16.7, 20.3 and 94.6 s match that decomposition without fitting anything.

With the tree-reduced validity check (256 rounds to 16), the two carry-free
updates should fall to roughly 7 and 10 seconds. That change is in the
repository but was deliberately not synced to these nodes, so the numbers
above describe the code as it was measured.

Garbling ran 76 minutes against the ~50 predicted from its loopback round
count, so BMR garbling is more latency-bound over a wide area than that count
suggests. It argues for stockpiling packages well ahead of need, not for
garbling on demand.

## The payment hot path, on its own

Review question from Paul, reading the update timings above: is it roughly
20 s per payment? No. Those figures are the prototype deriving the next
secret and revealing the current one back to back, with a compiler in the
loop. A payment only reveals a secret that is already prepared.

`programs/release_only.mpc` isolates exactly that: a public masked value,
one secret mask per online member, XOR, open.

| | rounds | traffic | WAN time |
|---|---:|---:|---:|
| one reveal | 6 | 160 B | **0.18 s** |
| one hundred reveals | 6 | 6.5 KB | 0.19 s, so **1.9 ms each** |

So the per-payment cost across three continents is under a fifth of a
second, and under two milliseconds when a busy endpoint batches. Everything
else measured in this file is preparation, and belongs off the payment path.

## Crash, quorum change and RESTORE

The full lifecycle with the standby member taking over
(`wan-live/lifecycle-crash-restore.txt`), cold start through the replicated
engine this time rather than a package:

```
== channel open: 48-edge cold start via replicated MPC
   cold start 3267.9s
== steady state: 2 updates
   state 0: point published (17.1s)
   state 1: point published, state 0 revoked (20.9s)
== crash: all volatile masks destroyed; member 2 offline
== quorum change to [0, 1, 3] + RESTORE from summands
   restored with 94 hashes in 7598.8s
== continuing: 2 updates with the new quorum
   state 2: point published, state 1 revoked (25.0s)
   state 3: point published, state 2 revoked (25.0s)
== distributed PoC complete: LDK accepted every point and secret
```

A quorum that lost a member in Ireland, replaced it with one in Frankfurt,
and had no volatile state left rebuilt the frontier from the seed summands
alone and continued the same channel, with the revocation pending at crash
time still completing. An unmodified rust-lightning counterparty accepted
every point and secret across the change.

**The cold start matches the model.** 3267.9 s for 48 edges is 68 s each,
against 65 s measured for a single edge, so a 48-hash program costs about
what 48 single hashes cost.

**Update times track the quorum's slowest leg.** Before the change the
quorum's worst leg was 117.8 ms and updates took 20.9 s; after it the worst
leg was 142.8 ms and updates took 25.0 s. The ratios are 1.21 and 1.20. The
same latency model predicts both, which is a stronger check than any single
figure here.

**RESTORE costs what the batching defect says it costs.** 7598.8 s for 94
hashes is 81 s each, and the 94 is itself the defect: the plan holds two
independent 47-hash walks, the frontier and one pending leaf, which sit at
the same depth and should cost one walk. See docs/batching.md.

## Reproducing

`wan/README.md` has the runbook. The phases that produced this file:

```sh
sh wan/prepare-aws.sh
sh wan/launch-instances.sh
sh wan/run-wan.sh mesh build certs ping bench
UPDATES=3 AFTER=0 COORD_ARGS=--skip-crash sh wan/run-wan.sh life
sh wan/teardown.sh
```
